Предлагаю построить конструктор импорта архитектурных артефактов с настраиваемыми пайплайнами преобразования, ручной верификацией и отслеживанием происхождения данных (Data Lineage / Provenance).

Это не просто парсер Confluence и не полноценная ETL-платформа. Это специализированное приложение для ведения архитектурных реестров, в котором автоматизация загрузки отделена от управления качеством и жизненным циклом архитектурных объектов.

## 1. Концепция решения

Полнотекстовый + семантический поиск • Проверка переноса • JSON API

Ключевое архитектурное решение: разделить исходный документ, результат его машинной интерпретации и утверждённый объект реестра.

Это три разных сущности, а не три состояния одной записи.

Такое разделение позволит менять алгоритмы извлечения, подключать локальные LLM, повторно обрабатывать документы и сравнивать результаты, не уничтожая ранее подтверждённые пользователем данные.

Я бы организовал приложение вокруг пяти рабочих областей. Важный принцип UX: пользователь работает с архитектурными объектами и правилами их заполнения, а не с техническими деталями ETL.

Это иллюстрация компоновки экранов, а не подключённое к реестру приложение.

Наиболее важный экран — верификация, где одновременно представлены оригинальный документ и формируемый объект. Пользователь должен видеть не только предложенное значение, но и почему оно предложено.

Для каждого поля следует показывать:

- предложенное значение и возможность его редактирования;
- способ извлечения: HTML-таблица, правило, скрипт, LLM или ручной ввод;
- фрагмент источника, откуда получено значение;
- результат проверки, наличие расхождения и статус подтверждения.

Для массовой работы нужен дополнительный режим табличной верификации: 50–100 объектов на одной странице, фильтр по ошибкам и массовое подтверждение только тех атрибутов, которые прошли детерминированные проверки.

## 3. Модель данных

Предлагаю следующие сущности. Они образуют основу доменной модели.

| Сущность             | Назначение                                             |
| -------------------- | ------------------------------------------------------ |
| `ArtifactType`       | Тип объекта реестра, JSON Schema, версия схемы         |
| `Artifact`           | Устойчивый ID, утверждённые реквизиты и статус         |
| `Source`             | Подключение к Confluence или источник файлов           |
| `SourceResource`     | Конкретная страница, вложение или загруженный документ |
| `SourceSnapshot`     | Сохранённая версия исходного содержимого               |
| `PipelineDefinition` | Версионированное описание шагов преобразования         |
| `ImportRun`          | Выполнение загрузки, ошибки, метрики                   |
| `ArtifactCandidate`  | Предложение создать или изменить объект                |
| `FieldEvidence`      | Происхождение конкретного значения атрибута            |
| `ArtifactSourceLink` | Связь объекта с одним или несколькими источниками      |

### Существенные ограничения модели

1\. Идентичность объекта не зависит от URL страницы. У объекта собственный UUID. URL и ID страницы — внешние идентификаторы. Поэтому к объекту, созданному вручную, позже можно прикрепить страницу Confluence.

2\. Один объект может иметь несколько оснований. Например, ADR, проектную презентацию и документ согласования. При этом нужно различать основной источник импорта и дополнительные подтверждающие материалы.

3\. Одна страница — один объект в рамках выбранной политики импорта. Для твоего первого сценария это ограничение фиксируется в `PipelineDefinition`, а не зашивается в движок. В будущем некоторые документы могут порождать несколько архитектурных объектов.

4\. Перезагрузка страницы не должна дублировать объекты. Нужна политика identity matching: по связи `SourceResource → Artifact`, по внешнему бизнес-ключу либо через ручное сопоставление. При обнаружении совпадения формируется предложение на обновление, а не новый объект.

5\. Ручное изменение имеет приоритет над повторным импортом. Новые значения помещаются в кандидата на обновление; ранее подтверждённое значение автоматически не перезаписывается.

Пример: архитектор вручную изменил «Проблематику» после первоначального извлечения из Confluence. Страница впоследствии изменилась. Система должна показать старое значение → текущее значение → новое предложение, а не молча заменить текст.

## 4. Дизайн Pipeline Engine

Предлагаю сделать гибридный движок, поддерживающий три способа преобразования:

| Способ                   | Применение                                                                       | Приоритет                           |
| ------------------------ | -------------------------------------------------------------------------------- | ----------------------------------- |
| Декларативные правила    | HTML-таблицы, CSS/XPath, регулярные выражения, поиск между заголовками           | Основной                            |
| Пользовательские скрипты | Сложные форматы, условная логика, нестандартные преобразования                   | Расширение                          |
| Локальные LLM            | Семантическое извлечение из свободного текста, переформулирование, классификация | Fallback или специализированный шаг |

Не стоит использовать LLM там, где есть устойчивый детерминированный алгоритм. Это повышает стоимость, время обработки и вероятность неконтролируемого изменения смысла.

### Структура одного пайплайна

1

Acquire

Получить страницу, вложение или файл

2

Parse

Преобразовать HTML/PPTX в нормализованное представление

3

Select

Выделить нужные таблицы, разделы или текстовые блоки

4

Transform

Применить маппинг, скрипты или LLM

5

Validate

Проверить JSON Schema и бизнес-правила

6

Match

Найти существующий объект или выявить дубликат

7

Review & Commit

Передать на проверку и сохранить

Каждый шаг принимает типизированное входное представление и возвращает результат. Для шагов должны сохраняться диагностические сведения: ошибки, входные данные, выходные данные и длительность исполнения.

Например, правило для поля «Проблематика» не требует программирования:

```

id: confluence-adr
version: 1
artifact_type: architecture_decision

source:
  type: confluence
  cql: 'space = ARCH AND label = "adr"'
  cardinality: one_per_page

steps:
  - id: parse
    use: html.to_document

  - id: extract_problem
    use: text.extract_between
    params:
      start: "Проблематика"
      end: "Задачи проекта"
      case_sensitive: false
      target: fields.problem

  - id: validate
    use: artifact.validate

  - id: propose
    use: artifact.create_candidate

```

Для извлечения между заголовками желательно предусмотреть не только буквальные маркеры, но и структурные границы документа: HTML heading, ячейка таблицы, параграф презентации. Иначе обычное появление фразы «Задачи проекта» внутри текста может преждевременно завершить извлечение.

### Расширяемость через скрипты

Я бы реализовал интерфейс шага с контрактом:

`InputDocument + Parameters → StepResult`

В `StepResult` входят значения полей, сведения об исходных фрагментах, предупреждения и ошибки.

Пользовательский скрипт должен иметь только ограниченный SDK для доступа к текущему документу. Прямой доступ к БД, секретам или сетевым API ему не нужен.

В MVP достаточно одного языка, например Python. Запуск — в изолированном worker/container с ограничением времени, памяти, файловой системы и сетевых возможностей. Просто запускать пользовательский Python через `exec()` внутри backend-процесса небезопасно.

Дополнительно нужен экран тестирования шагов на эталонных документах. После изменения кода пользователь должен видеть, какие реквизиты изменились и какие тестовые примеры перестали обрабатываться.

| Источник        | Адаптер                       | Важная особенность                                                        |
| --------------- | ----------------------------- | ------------------------------------------------------------------------- |
| Confluence Page | CQL + REST                    | Сохранять page ID, version, storage content                               |

| Ручной ввод     | Form adapter                  | Не требовать наличия SourceResource                                       |
| Локальная LLM   | LLM transformation step       | Использовать для преобразования, а не как самостоятельный источник истины |

Два нюанса реализации:

Во-первых, Confluence Storage Format не следует считать обычным HTML: он содержит специальные элементы и макросы. Поэтому стоит сохранять оригинальное содержимое и строить промежуточную модель документа. Если требуется результат выполнения макроса, может понадобиться отдельный режим получения rendered content.

Во-вторых, при массовом импорте лучше сначала получать список page ID и метаданные по CQL, а затем загружать содержимое страниц отдельно. Atlassian документирует ограничения размера выборки при запросах с расширением `body`.&#x20;

## 6. Промежуточный формат документа

Это один из самых полезных элементов дизайна.

Вместо того чтобы каждый pipeline самостоятельно понимал HTML или PPTX, я бы ввёл единый `NormalizedDocument`:

NormalizedDocument

Общее представление для всех форматов

Metadata

Sections

Paragraphs

Tables

Links

Attachments

Text spans

Source anchors

Тогда одна и та же логика извлечения раздела «Проблематика» может работать и с HTML, и с PPTX, несмотря на различия их внутренней структуры.

При этом `SourceAnchor` фиксирует происхождение фрагмента: XPath/идентификатор элемента для HTML, номер слайда и идентификатор shape для PPTX, а также текстовую цитату. Это необходимо для последующей верификации.

Текст из презентации можно извлекать стандартным PPTX-парсером. Но таблицы, SmartArt, встроенные изображения и графические схемы требуют отдельной стратегии. Я бы не включал OCR и мультимодальный анализ в первую версию без подтверждённой потребности.

## 7. Подключение локальных LLM

Я бы сделал LLM обычным сменным исполнителем шага преобразования, а не ядром приложения.

Пример контракта шага:

- вход: нормализованные фрагменты документа, описание нужных реквизитов, JSON Schema;
- выход: значения реквизитов, привязка к фрагментам, предупреждения;
- обязательная проверка: JSON Schema плюс прикладные правила;
- режим исполнения: ручной, условный или автоматический.

Для Ollama доступен Structured Output с передачей JSON Schema в параметре `format`. Это полезно для типизированного извлечения, но не гарантирует фактической корректности значений.&#x20;

## 8. Поиск и контроль качества

Для поиска предлагаю гибридную модель:

Лексический поиск — по названию, реквизитам, системным идентификаторам, точным терминам и ключевым словам.

Семантический поиск — по смыслу описания, проблематики и решения. Например, запрос «исключить потерю сообщений при передаче в АБС» может находить объекты про Inbox, replay и гарантированную доставку.

Технически для MVP достаточно PostgreSQL: full-text search, `pg_trgm` для неточных совпадений и `pgvector` для семантики. pgvector поддерживает совмещение полнотекстового и векторного поиска, в частности через Reciprocal Rank Fusion.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub+1



Контроль качества стоит сделать самостоятельной функцией, а не одной условной оценкой confidence.

| Метрика               | Что показывает                                                     |
| --------------------- | ------------------------------------------------------------------ |
| Completeness          | Доля заполненных обязательных реквизитов                           |
| Evidence coverage     | Доля реквизитов с проверяемым источником                           |
| Auto-accept rate      | Доля автоматически предложенных значений, принятых без исправлений |
| Correction rate       | Доля исправленных пользователем значений                           |
| Duplicate rate        | Частота обнаружения уже существующих объектов                      |
| Freshness             | Наличие более новой версии исходного документа                     |
| Extraction error rate | Доля документов, не прошедших обработку                            |

Отдельно важно сравнивать качество пайплайнов между собой. Например, новый LLM-шаг может заполнить больше полей, но при этом увеличить correction rate. Без этих метрик автоматизацию легко ошибочно принять за улучшение качества данных.

## 9. Техническая реализация

Для небольшого внутреннего продукта я бы выбрал modular monolith + asynchronous workers, а не микросервисную архитектуру.

Frontend — React / TypeScript

Registry UI • Review UI • Pipeline Designer

Backend — Python / FastAPI

Artifact Registry

Schema Registry

Source Connectors

Pipeline Orchestrator

Review & Governance

Search API

PostgreSQL

JSONB + pgvector

Object Storage

Snapshots / files

Workers

Parsers / LLM / Scripts

Для фоновых задач подойдёт очередь Redis + Celery/RQ. PostgreSQL хранит объекты, схемы, связи, результаты выполнения и audit trail. Исходные файлы и snapshots — в объектном хранилище либо файловом хранилище на раннем этапе.

Важные эксплуатационные требования: повторяемость операций, идемпотентность импорта, retry с ограничениями, сохранение ошибок по документам и возможность повторного исполнения только проблемных элементов.

Отдельный Elasticsearch/OpenSearch или тяжёлый workflow engine на старте не нужен, пока объём и сложность не обосновывают дополнительные операционные затраты.

| Конструктор правил         | Редактор пайплайнов, готовые операции, sandbox для скриптов, тесты, версии                                      | Self-service настройка импорта                             |

На первом этапе я бы сознательно ограничил число типов объектов и сценариев импорта, но сразу реализовал идентичность объекта, связь с источником, версионирование и непротиворечивое обновление. Их последующее добавление будет значительно дороже, чем добавление очередного парсера.

## 11. Архитектурные риски и решения

| Риск / anti-pattern                             | Последствие                                 | Рекомендуемое ограничение                     |
| ----------------------------------------------- | ------------------------------------------- | --------------------------------------------- |
| Объект реестра равен странице Confluence        | Невозможность независимого жизненного цикла | Отдельные Artifact и SourceResource           |
| Автоматический upsert без diff                  | Потеря ручных корректировок                 | Кандидаты на изменения                        |
| Универсальный пользовательский код без изоляции | Нестабильность и риск безопасности          | Sandbox + ограниченный SDK                    |
| LLM как обязательный этап                       | Непредсказуемое качество, latency, нагрузка | Детерминированные правила по умолчанию        |
| Произвольный JSON без типизированных схем       | Деградация качества и поиска                | JSON Schema и версии                          |
| Вся история только в логах                      | Невозможно доказать качество переноса       | FieldEvidence и ImportRun                     |
| Автоматическая загрузка без ownership           | Реестр постепенно становится недостоверным  | Владельцы типов объектов и правила публикации |

Особенно важно разграничить ответственность:

Владелец типа архитектурного объекта определяет структуру реквизитов и правила качества. Разработчик пайплайна отвечает за преобразование. Архитектор или steward реестра подтверждает корректность содержимого. Это могут быть одни и те же люди в небольшой команде, но роли лучше разделить концептуально с самого начала.

## 12. Итоговая рекомендация

Я вижу здесь три возможных уровня продукта.

1. Registry Importer — специализированная загрузка в архитектурный реестр. Самый простой вариант, но с ограниченной расширяемостью.
2. Registry Studio — реестр + конструктор пайплайнов + подтверждение изменений + управление источниками. Именно его рекомендую как целевую модель.
3. Enterprise Knowledge ETL Platform — универсальная система извлечения корпоративных знаний. Потенциально мощнее, но рискует превратиться в самостоятельную платформу со значительными затратами на разработку и сопровождение.

Для твоих кейсов второй вариант даёт наиболее рациональный баланс.

Следующим шагом я бы детализировал именно Registry Studio в виде интерактивного HTML-прототипа с тремя сквозными пользовательскими сценариями: создание коллекции Confluence и пайплайна, верификация извлечённого объекта, а также ручное создание объекта с последующей привязкой к странице. Это позволит проверить UX и доменные границы до реализации backend.
