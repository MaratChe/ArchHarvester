# Architecture Registry Studio

Локальное приложение для одного пользователя: преобразование HTML, PPTX и страниц Confluence в объекты архитектурного реестра с проверкой перед сохранением. Версия **0.8.0**. Интерфейс — на русском языке.

Реестр и исходники хранятся на компьютере. Для извлечения можно использовать правила, Python, локальную Ollama или OpenAI-совместимые API. При выборе внешнего провайдера выбранный текст отправляется на его сервер; адрес отображается в интерфейсе.

## Возможности

- Ручное создание объектов, черновики, публикация, история ревизий и JSON-экспорт.
- Конструктор типов: реквизиты, описания, обязательность, варианты значений и версии схем.
- Импорт HTML/PPTX, страницы Confluence по CQL, PPTX-вложения через API с PAT.
- Версионируемые пайплайны: таблицы, разделы, текст между границами, Python, JavaScript (Node.js Worker) и LLM.
- Собственные LLM-инструкции, контекст предыдущих шагов, полный запрос и ответ в отчёте тестирования.
- Проверка предложений по цитатам и снимкам; ручные значения не перезаписываются автоматически.
- Поиск по словам и смыслу, ссылки на источники и исключение устаревших векторов.

## Требования

Основная среда — **Windows и PowerShell**. Установщика/службы Windows пока нет: приложение разворачивается из исходников.

| Компонент | Назначение |
|---|---|
| Python **3.13** с pip | Backend и виртуальное окружение |
| Node.js **22.12+** и npm | Установка зависимостей и сборка интерфейса; при обычном запуске не нужны |
| Git | Клонирование и обновление исходников |
| Docker Desktop с Linux containers | Для пользовательских Python- и JavaScript-шагов |
| Ollama | Только для локальных LLM и embeddings |
| Доступ к Confluence/VPN или API-провайдеру | Только для соответствующих интеграций |

Для ручного реестра, HTML/PPTX, правил и поиска по словам Docker и Ollama не требуются. PostgreSQL, Redis и отдельный веб-сервер не нужны.

Проверка инструментов:

```powershell
git --version
python --version
python -m pip --version
node --version
npm.cmd --version
```

Используйте Python 3.13 для создания `.venv`. Скрипт установки использует `pip --python`, доступный в pip 22.3+.

## Развёртывание с нуля

### 1. Получить исходники

Скопируйте проект в выбранный каталог, например `C:\dev\arch_parser`. Если настроен удалённый репозиторий, его можно клонировать:

```powershell
git clone https://github.com/MaratChe/ArchHarvester.git C:\dev\arch_parser
Set-Location C:\dev\arch_parser
```

Следующие команды выполняются **из корня проекта**.

### 2. Установить зависимости

```powershell
.\scripts\setup.ps1
```

Скрипт создаёт `.venv`, устанавливает версии из `backend/requirements.lock`, выполняет `npm ci` по `frontend/package-lock.json` и собирает `frontend/dist`. Первая установка требует сети. Активация виртуального окружения не нужна.

Если PowerShell блокирует запуск скрипта, можно разрешить его только для этого процесса, без изменения системной политики:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup.ps1
```

### 3. Запустить приложение

```powershell
.\scripts\start.ps1
```

Откроется браузер: **http://127.0.0.1:8765/**. Оставьте окно PowerShell работающим. Остановка — **Ctrl+C** в этом окне. Миграции SQLite применяются при запуске.

Варианты запуска (выберите один):

```powershell
# Без автоматического открытия браузера
.\scripts\start.ps1 -NoBrowser

# Другой порт и отдельный каталог данных
.\scripts\start.ps1 -Port 8766 -DataDir 'C:\RegistryData' -NoBrowser

# Если локальная политика блокирует .ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 -NoBrowser
```

Не запускайте несколько экземпляров с общей БД. Если порт занят, остановите предыдущий экземпляр или используйте другой порт; для независимого второго реестра задайте другой `-DataDir`.

### Запуск через Git Bash (Windows)

```bash
bash scripts/setup.sh
bash scripts/start.sh
# Дополнительные параметры:
bash scripts/start.sh --port 8766 --data-dir '/c/Registry Data' --no-browser
# Только для Python-шагов (требуется запущенный Docker Desktop):
bash scripts/setup-python-runner.sh
```

Скрипты `.sh` рассчитаны на Git Bash из Git for Windows и вызывают Windows PowerShell. Это не установка для WSL/Linux. Они работают из любого текущего каталога, если указан правильный путь к скрипту; активация `.venv` не нужна. `bash scripts/start.sh --help` показывает параметры.

### HTTPS и корпоративные сертификаты

Confluence (включая вложения) и все OpenAI-совместимые провайдеры, в том числе LiteLLM, используют системные доверенные CA через Python `ssl.create_default_context()`. На Windows загружаются системные хранилища `ROOT` и `CA`. Проверка цепочки и имени сервера включена всегда.

Если корпоративный CA ещё не установлен в системе, приложите PEM-файл с одним или несколькими сертификатами корневых/промежуточных CA при запуске:

```powershell
.\scripts\start.ps1 -CaBundle 'C:\Certificates\corporate-ca.pem'
```

```bash
bash scripts/start.sh --ca-bundle '/c/Certificates/corporate-ca.pem'
```

Альтернатива для прямого запуска backend — переменная окружения `ARCH_REGISTRY_CA_BUNDLE` с абсолютным Windows-путём к PEM-файлу. Дополнительные CA дополняют системное доверие и применяются ко всем подключениям Confluence и LLM в этом процессе. После изменения настройки перезапустите приложение. Отсутствующий или некорректный файл вызывает ошибку запуска; приложение не отключает TLS-проверку. Файл хранится у вас, не копируется в БД и не загружается через интерфейс.

Нужны именно публичные сертификаты CA в PEM (`BEGIN CERTIFICATE`), без приватного ключа. PFX/P12 и клиентская аутентификация mTLS здесь не поддерживаются. Настройка относится к HTTPS-запросам приложения; установка зависимостей pip/npm использует собственные настройки сертификатов этих инструментов.

Проверка готовности во втором окне PowerShell:

```powershell
$session = Invoke-RestMethod http://127.0.0.1:8765/api/session
$session | Select-Object version, data_dir
```

Не публикуйте значение `token` этого ответа. Интерфейс обрабатывает его автоматически.

Сервис привязан к loopback. Публичное серверное развёртывание, публикация порта и многопользовательский доступ в этой версии не поддерживаются.

## Первое использование

1. В «Типы объектов» создайте тип или используйте «Архитектурное решение».
2. Создайте объект вручную либо загрузите `tests/fixtures/decision-table.html` через «Загрузка файлов».
3. Проверьте предложения рядом с исходником, исправьте поля и подтвердите публикацию.
4. Для повторного импорта используйте «Загрузить новую версию» в карточке основания, чтобы сохранить связь с источником.
5. В «Пайплайны» создайте шаги, сохраните версию, проверьте её на снимках и опубликуйте.

Файлы `tests/fixtures` синтетические. Личные документы и результаты обработки не добавляйте в Git.

## Дополнительные интеграции

### Confluence

В разделе «Confluence» укажите base URL и PAT для on-premise Confluence 7.13.7, проверьте CQL, выберите страницы и запустите импорт. PAT сохраняется в Windows Credential Manager. Приложение читает источники и не изменяет Confluence.

Инструкции: [Confluence](docs/confluence.md), [PPTX-вложения](docs/pptx-pipelines.md).

### Ollama

Запустите Ollama на этом компьютере. Встроенное подключение использует `http://127.0.0.1:11434`. Проверить установленные модели:

```powershell
ollama list
```

В «Модели и API» выберите «Локальная Ollama» и модель из каталога. Исходные значения: `ornith-1.5:9b` для извлечения, `bge-m3:latest` для embeddings. Модели **не поставляются с приложением** и могут отсутствовать на новой машине: установите необходимые средствами Ollama либо выберите уже установленные. Требования к RAM/VRAM зависят от модели.

Для поиска нажмите «Построить / обновить индекс», затем выберите «По смыслу и словам» в реестре. После изменения объектов индекс нужно обновлять вручную.

Инструкция: [Ollama и поиск](docs/ollama.md).

### OpenRouter, LiteLLM и другие совместимые API

В «Модели и API → Подключения OpenAI API» задайте имя, base URL и Bearer-ключ. Примеры: `https://openrouter.ai/api/v1`, `http://127.0.0.1:4000/v1` для локального LiteLLM. Для удалённых серверов нужен HTTPS. Модель можно выбрать из каталога либо ввести вручную.

Провайдеры извлечения и embeddings выбираются независимо. LLM-шаг сохраняет свой provider ID. Ключи находятся в Windows Credential Manager, а не в `.env` или SQLite.

Инструкции: [подключения API](docs/providers.md), [инструкция и контекст LLM](docs/llm-step-context.md), [просмотр запросов и ответов](docs/llm-diagnostics.md).

### Python-шаги

Установите и запустите Docker Desktop в режиме Linux containers, затем:

```powershell
docker version
.\scripts\setup-python-runner.ps1
```

Собирается образ `architecture-registry-python:2`. Шаг работает в одноразовом контейнере без сети/доступа к БД и секретам, с ограничениями времени и ресурсов. При отсутствии Docker пользовательский Python не выполняется внутри backend.

Пайплайны закрепляют ID образа. На другой машине или после пересборки может понадобиться новая версия пайплайна с повторным тестом и публикацией.

Инструкция: [правила и Python](docs/pptx-pipelines.md).

## Данные и резервные копии

По умолчанию: `%LOCALAPPDATA%\ArchitectureRegistryStudio\`. Параметр `-DataDir` переопределяет путь; backend также читает `ARCH_REGISTRY_DATA`. Фактический путь виден в разделе типов и `/api/session`.

- `registry.db` и SQLite companion files: типы, объекты, ревизии, кандидаты, пайплайны, задания, индексы.
- `blobs/`: неизменяемые HTML/Storage XML/PPTX по хешам.
- Windows Credential Manager: PAT Confluence и API-ключи (отдельно от каталога данных).

Диагностика LLM содержит текст документов/запросов и хранится локально 7 дней; HTTP-заголовки и API-ключи в неё не включаются.

**JSON-экспорт — не полная резервная копия.** Дождитесь завершения операций, остановите приложение через Ctrl+C и скопируйте весь каталог данных вместе с `blobs` и существующими SQLite companion files. Не копируйте только `registry.db` во время работы.

Пример для стандартного каталога, **после остановки сервиса**:

```powershell
$registryData = Join-Path $env:LOCALAPPDATA 'ArchitectureRegistryStudio'
$backupRoot = Join-Path ([Environment]::GetFolderPath('MyDocuments')) 'ArchitectureRegistryBackups'
New-Item -ItemType Directory -Force -Path $backupRoot | Out-Null
$backupTarget = Join-Path $backupRoot (Get-Date -Format 'yyyyMMdd-HHmmss')
Copy-Item -LiteralPath $registryData -Destination $backupTarget -Recurse
```

Для восстановления скопируйте резервную копию в **новый пустой каталог** и запустите `start.ps1 -DataDir 'путь_к_восстановленной_копии'`. Не запускайте приложение на единственной резервной копии. На другом компьютере API-ключи/PAT нужно ввести заново: они не входят в копию БД. Автоматического backup и мастера восстановления пока нет.

## Обновление

1. Завершите операции, остановите сервис и сделайте полную резервную копию данных.
2. Обновите исходники. Если remote настроен и локальные изменения сохранены, можно использовать `git pull --ff-only`.
3. Выполните `scripts/setup.ps1`, затем `scripts/start.ps1` с прежним каталогом данных.
4. Обновите страницу браузера: после перезапуска меняется токен локальной сессии.

Не запускайте установку поверх работающего приложения: она заменяет frontend build. При переносе на другую машину создавайте `.venv` заново; не копируйте окружение и `node_modules`.

## Ограничения и диагностика

- Windows Credential Manager нужен для хранения ключей. Linux/macOS как полная поставка не проверены.
- LLM-вход: до 12000 UTF-8 байт вместе со схемой/инструкцией/контекстом, до 200 блоков. Большие документы пока делятся вручную.
- OCR, изображения/SmartArt и графические схемы PPTX не распознаются. Сложные таблицы могут пропускаться с предупреждением.
- Индекс пилотный: до 5000 объектов и 5 млн компонент векторов; при 1024 измерениях лимит компонент может сработать раньше. Перестройка ручная.
- Реальные корпоративные Confluence/OpenRouter/LiteLLM требуют приёмки после настройки доступа. Полная проверка на чистой Windows и нагрузочные измерения остаются открытыми задачами.

| Симптом | Действие |
|---|---|
| Порт 8765 занят | Остановить старый экземпляр или выбрать `-Port` |
| Ошибка локального токена после перезапуска | Обновить страницу браузера |
| Не найден frontend build | Выполнить `scripts/setup.ps1` |
| Ollama/модель недоступна | Проверить сервис и `ollama list`, выбрать установленную модель |
| Python-шаг недоступен | Запустить Docker Desktop, собрать runner |
| API 401/403 | Проверить ключ и права подключения; не помещать ключ в URL |
| Индекс устарел | Перестроить в «Модели и API»; поиск по словам остаётся доступен |

Дополнительно: [конструктор типов](docs/type-builder.md), [первичный анализ](docs/problem_analize.md), [план реализации](docs/implementation_plan.md).


## JavaScript Script Engine

В редакторе пайплайна доступен шаг **Script Engine (JS)**: код JavaScript, JSON-параметры, HTML → Markdown, предложения реквизитов с проверкой схемы и источников. Markdown можно просмотреть и скачать из отчёта тестирования и формы проверки предложения.

Подготовка: `./scripts/setup-javascript-runner.ps1` или `bash scripts/setup-javascript-runner.sh` в Git Bash. Требуется Docker Desktop; Node.js Worker выполняется внутри контейнера без сети и файлов компьютера.

[Контракт, пример кода, настройка и проверка результата](docs/javascript-engine.md).


## Массовый импорт решений АК

В разделе Confluence после поиска CQL выберите режим PPTX-вложений: каждая презентация становится отдельным основанием решения; новые версии обновляют связанный объект после проверки. [Инструкция](docs/confluence-pptx-bulk.md).

### Передача результатов шагов

Python и JavaScript получают `previous_results` и передают JSON через `set_output(...)`. В тестировании доступен вход и выход каждого шага, включая шаг с ошибкой. [Контракт и пример HTML → Markdown → реквизиты](docs/pipeline-step-data.md). После обновления пересоберите оба Docker-исполнителя: `scripts/setup-python-runner.ps1` и `scripts/setup-javascript-runner.ps1` (для Git Bash — одноимённые `.sh`). Для использования нового SDK сохраните и протестируйте новую версию пайплайна: опубликованные версии сохраняют прежние образы.
