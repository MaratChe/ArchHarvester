# Данные между шагами пайплайна

Python и JavaScript выполняются последовательно в отдельных ограниченных Docker-контейнерах. Переменные процесса и временные файлы между ними не сохраняются. Для передачи данных используйте JSON-контракт:

- `document` — исходный документ с неизменными block IDs; `params` — параметры текущего шага.
- `previous_results.fields` — накопленные проверенные реквизиты с доказательствами.
- `previous_results.conflicts` — поля, исключённые из предложений из-за конфликта.
- `previous_results.steps` — список завершённых шагов по порядку: `index` (с 1), `kind`, `output`, `emitted_fields`, `warnings`, а для JS также `files` и идентификатор исполнителя.
- `set_output(value)` — сохраняет JSON-значение текущего шага: объект, массив, строку, число, boolean или null. Последний вызов заменяет предыдущий. Без вызова выход равен null. Лимит — 256 KiB UTF-8; NaN/Infinity, циклы и значения вне JSON запрещены.
- `emit(field, value, block_ids)` — создаёт предложение реквизита. `set_output` сам по себе реквизиты не меняет и объект не сохраняет.

Первый шаг получает пустые `steps`, `fields` и `conflicts`. Для последующих последний результат доступен как `previous_results['steps'][-1]['output']` в Python или `previous_results.steps.at(-1).output` в JS. Можно обращаться к любому более раннему шагу по индексу списка или искать по `index`.

Изменения `document`, `params` или `previous_results` внутри скрипта не изменяют источник, предыдущие результаты и вход следующего шага. Передайте преобразованные данные явно через `set_output`. Для пропуска данных через промежуточный скрипт вызовите `set_output` с нужным предыдущим значением. Правила table/sections/between сохраняют обычную работу с исходным документом; их результаты доступны через `fields`.

## Пример: HTML → Markdown → реквизит

Шаг 1, JavaScript:

```javascript
const markdown = toMarkdown(document.html);
saveMarkdown('page.md', markdown);
set_output({
  markdown,
  source_ids: document.blocks
    .filter(b => b.text.startsWith('Владелец:'))
    .map(b => b.id)
});
```

Шаг 2, Python:

```python
data = previous_results['steps'][-1]['output']
owner = next(
    (line.split(':', 1)[1].strip()
     for line in data['markdown'].splitlines()
     if line.startswith('Владелец:')),
    None
)
if owner and data['source_ids']:
    emit('owner', owner, data['source_ids'])
set_output({'owner': owner, 'source_ids': data['source_ids']})
```

Шаг 3 может преобразовать `owner` или использовать другой промежуточный результат. Если он снова выдаёт `owner`, включите «Разрешить этому шагу заменить предложения предыдущих шагов». Ссылки должны указывать на блоки исходного документа, а не строки полученного Markdown. Сервер по-прежнему проверяет схему и доказательства; LLM также проверяет точность цитат.

Markdown-файлы JS доступны в `previous_results.steps[…].files` как `{name, content}`. Наличие файла не создаёт отдельный объект реестра.

## Просмотр теста

Сохраните новую версию, выберите снимок и нажмите «Проверить версию». Под документом раскройте «Шаг N … результаты», затем:

- **Вход шага**: документ, параметры, настройки и переданный контекст.
- **Выход шага**: выданные предложения, `output`, файлы, предупреждения, накопленные поля и конфликты.

При ошибке сохраняются завершённые шаги и вход ошибочного; последующие не выполняются. Если ошибка возникла до получения результата, выхода нет. Полученный, но отклонённый при проверке ответ не считается успешно применённым. Для LLM точный API-запрос и сырой ответ остаются в отдельной LLM-диагностике. При `include_previous=true` модель получает также JSON-выходы и файлы предыдущих шагов; общий бюджет LLM остаётся 12000 байт.

Вход и выход в отчёте ограничены отдельно 512 KiB: большие записи содержат `truncated: true`, полный размер и начало JSON в `preview`. Это ограничение отображаемой диагностики, а не скрытое усечение входа исполнителя. Общий вход контейнера по-прежнему ограничен 16 MiB, вывод — 1 MiB. Полные входы сохраняются только в отчётах тестирования, не в каждом предложении импорта. Старые отчёты не дополняются автоматически — повторите тест.

## Обновление исполнителей

Соберите `scripts/setup-python-runner.ps1` и `scripts/setup-javascript-runner.ps1` (Git Bash: одноимённые `.sh`). Новые образы имеют теги `architecture-registry-python:2` и `architecture-registry-javascript:2`.

Старый код без `set_output` остаётся рабочим. Опубликованные пайплайны сохраняют закреплённые image IDs; они не получают новый SDK автоматически. Для передачи данных сохраните новую версию, выполните тест и опубликуйте её. Изменений схемы БД нет: новые поля хранятся в существующем JSON отчётов и результатов.
